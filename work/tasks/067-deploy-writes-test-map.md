## Context

- **The user asked for the map (2026-08-13T08:28Z):** *"can you make me a saved
  map where i can quickly test our features?"* Task 062 built it (PR #93,

- **The defect, in the user's own words on the card they read at 9am:**
  `tools/feature-test-map-card.md` line 3 currently says

  > **Not in the map list?** A redeploy deletes it -- that is being fixed
  > separately.

  **That line is your other deliverable.** When the map survives, the line is
  wrong and must go. Do not leave a card that tells the user to work around a
  problem that no longer exists — a stale workaround costs more than no card.
- **Why it happens.** `tools/deploy.ps1` mirrors `-SourceGameDir` (default
  `C:\sc-work\1161-base`) into `<DeployRoot>\game` with robocopy `/MIR`.
  `/MIR` purges anything in the destination that is not in the source. The
  script already excludes `characters\`, `save\`, `Maps\Replays\` and
  `maps\download\` from the mirror in both directions — **so the exclusion
  mechanism exists and works; the map just is not covered by it.**
- **The map**: `!feature-test.scx`, generated by
  `tools/make-feature-test-map.ps1`, named with a leading `!` on purpose so it
  sorts to the top of the map browser. Card: `tools/feature-test-map-card.md`.
- **Hard rule 1 still binds.** A `.scx` is game content and is NEVER committed.
  Whatever you do, the map is generated at deploy time or preserved across the
  mirror — it does not enter the repo.
- **Two shapes are available and they have different costs. Pick with evidence,
  and say why:**
  1. **Generate after the mirror** — deploy runs `make-feature-test-map.ps1`
     against the deployed tree as a final step. Simple, always fresh, and the
     map matches the build that was just deployed. Costs a generator run on
     every deploy and needs the venv/richchk available at deploy time (see
     issue #97 — the interpreter question is live).
  2. **Preserve it across the mirror** — add the map to the same exclusion set
     that already protects `save\` and `characters\`. Cheaper, no generator
     dependency, but a stale map survives a build it no longer matches, and the
     user would have no signal that it is stale.
  **State the trade-off you chose and the failure mode you accepted.**
- **`tests/deploy-runtime.Tests.ps1` exists** — read it before changing
  `deploy.ps1`. The script also verifies preserved directories before and after
  the mirror and throws if anything preserved actually changed; whatever you add
  should fit that existing shape rather than bolt beside it.
- **Do NOT write user state.** `deploy.ps1`'s whole design is about not
  destroying what the deployed game writes. The 2026-07 registry-wipe incident
  is the house rule here: never write the user's live state — and their
  `Maps\BroodWar` tree contains maps they may have put there themselves.
  **Purging or overwriting anything of theirs to make room is not acceptable.**
- **This is a hobby project.** The user wants to double-click a map after a
  redeploy. One working path beats a configurable one.
