Handoff for whoever gets part 1. Ten lines, only what the PR doesn't already say.

1. I did not run any real suite yet -- part 0 was pure mechanism work (sc-desktop.ps1,
   run-offscreen.ps1) plus synthetic `-Command` probes. No dropdown/suite-specific findings to
   hand over beyond what's already in the README's task-043 section and this task file's Context.
2. `-SuiteArgs` reaches the child via Clixml (`Export-Clixml`/`Import-Clixml`), not command-line
   quoting -- safe for hashtables, switches, spaced paths. `-Command`, by contrast, is spliced into
   the child script as raw text via an expandable here-string; a `-Command` value containing an
   unescaped `"@` would corrupt the generated child script. Suites only ever go through
   `-SuiteArgs`, so this is a `-Command`-only footgun, not a suite one -- but worth knowing before
   reaching for `-Command` to probe something.
3. The real desktop-teardown race (part 0's bug) could NOT be forced from outside via chained
   `run-offscreen.ps1` calls reusing a desktop name -- 20 attempts, no hit, timing too tight for a
   subprocess-driving script to control. If part 1 hits a suite that intermittently fails with the
   host-startup-crash signature (Win32 0xE9 / "no run-offscreen(child): line"), that's the same
   class, now caught loudly instead of silently -- don't spend spawns trying to force it
   reproducibly, the guard is already proven via the exit-code path (see PR #57).
4. `Assert-ScDesktopHidden` itself never surprised me -- it does exactly what its docstring says.
   The surprise was one level up: `CREATE_NEW_CONSOLE` (now `CREATE_NO_WINDOW`) had nothing to do
   with desktop correctness and everything to do with Windows Terminal's DefTerm hand-off ignoring
   `lpDesktop` -- a genuinely separate mechanism from the desktop-object isolation task 043 built.
5. Spawn-budget caution from part 0 (console-flash risk) no longer applies the same way now that
   `CREATE_NO_WINDOW` is merged -- ordinary off-screen suite runs shouldn't disturb the user's
   screen at all. Part 1's real constraint is machine/game-lock contention with other workers
   (`sc-launch-lock.ps1`), not spawn count -- 18 suites, each launching the actual game, is a
   different kind of "ask first" than console spawns were.
