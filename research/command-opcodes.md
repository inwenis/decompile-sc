# Every command opcode StarCraft.exe 1.16.1 accepts, and whether it may be fanned out

Analysis date: 2026-08-08 (task 015). Target: `StarCraft.exe`, StarCraft: Brood War 1.16.1
(classic), SHA-256 `AD6B58B27B8948845CCFA69BCFCC1B10D6AA7A27A371EE3E61453925288C6A46` — the
project's disposable working copy `C:\sc-work\1161-base`, hash checked before and after every
run in this document.

Companion to [`command-path.md`](command-path.md) (task 011), which mapped the **send** side:
one funnel, 51 emitted ids, two payload layouts, and 45 ids deliberately left unnamed. This
document is the **receive** side, because that is where the question this task exists to answer
actually lives: *what does the engine DO with each command?* A fan-out replays a command against
the units the 12-cap hid, so the only safe rule is one derived from what the engine already does
with its own twelve.

Committed table: [`data/command-opcodes.tsv`](data/command-opcodes.tsv), regenerated by
`tools/ghidra/build-opcode-policy.ps1`.

---

## 0. Verdict up front

1. **The command-length table is at `0x005005F8`.** One dword per opcode id: the length the
   engine consumes, `0xFFFFFFFF` for an id it does not accept, and the *maximum* length for a
   variable-length one. Found by matching it against the 46 fixed emit-site lengths task 011
   already had — 44 of 46 agree, and both disagreements are explained rather than waved away.
   §1.
2. **There is one receive-side dispatcher: `0x004865D0`.** A switch over 58 opcode ids, each
   case consuming a fixed byte count and calling one handler. It is the authority on lengths;
   the table at `0x005005F8` is consulted only on its skip path. §2.
3. **The policy falls out of one property of each handler**, and nothing else:

   > **fan out a command ⟺ its handler applies it to EVERY unit in the receiving player's
   > selection, AND the handler does not move the player's resources.**

   19 of the 58 accepted opcodes qualify. §3, §5.
4. **Two opcodes are named from in-game keypresses**: `0x1A` is **Stop** (key S) and `0x2B` is
   **Hold Position** (key H). Attack, Patrol and Move are all `0x15` (Targeted Order) with
   different order bytes. Nothing else is named — same discipline as
   [`command-path.md`](command-path.md) §6. §4.
5. **The engine has no spell arbitration.** A targeted order is given to every selected unit;
   there is no "one caster" logic anywhere on the path. At twelve casters the engine makes
   twelve casts, so fan-out at twenty-four makes twenty-four. §6.
6. **No stock map can host a >12 homogeneous untargeted-ability test.** All 210 stock maps
   scanned; the reason is structural, not bad luck, and a future task wanting the same fixture
   will hit the same wall. §8.

## 1. The command-length table (`0x005005F8`)

### 1.1 How it was found

Not by pattern-matching a guess. [`data/command-ids.tsv`](data/command-ids.tsv) already carried
46 opcode ids whose emitted length is a literal at the call site. Those 46 (id, length) pairs are
a fingerprint: any byte- or word- or dword-strided array in the binary that reproduces them,
indexed by id, is the length table. `work/scratch/015/find_len_table2.py` swept **every file
offset** for strides 1, 2, 4, 6, 8, 10, 12, 16 and element widths 1, 2, 4, scoring each candidate
against all 46 constraints and reporting anything within six mismatches.

Exactly one candidate came back, at every width tried: **file offset `0x1005F8`, VA
`0x005005F8`, in `.rdata`, stride 4, 44 of 46 exact.** No second candidate scored above 40.

### 1.2 What is in it

```
idx   VA          dword       meaning
0x00  0x005005F8  0xFFFFFFFF  not a command
...
0x09  0x0050061C  0x0000001A  Select        -- 26 == 2 + 12*2, the MAXIMUM select length
0x0A  0x00500620  0x0000001A  SelectAdd     -- same
0x0B  0x00500624  0x0000001A  SelectRemove  -- same
0x14  0x00500648  0x0000000A  Right Click   -- 10
0x15  0x0050064C  0x0000000B  Targeted Order-- 11
...
0x5C  0x00500768  0x00000052  82
0x5D..0x75         0xFFFFFFFF  not commands
0x76  0x005007D0  0x7F800000  unrelated .rdata (a float +inf); the table ends before here
```

The three select entries are the strongest single confirmation available: `0x1A` is exactly
`2 + 12*2`, the largest a 12-slot selection command can be, and nothing about the search
assumed it — those three ids are `computed` at their emit sites and contributed **no**
constraint to the sweep.

### 1.3 The two disagreements, and why neither is a problem

| id | table | emit site | reading |
|---|---|---|---|
| `0x37` | 1 | 7 | The dispatcher consumes **7** for `0x37` and handles it on the path that never consults the table (§2.1). The table entry is dead code for this id. The 7 is right; it is also what the plugin observes on the wire (`CMD id=0x37 len=7`). |
| `0x54` | `0xFFFFFFFF` | 1 | The dispatcher has **no case for `0x54`**: the engine does not accept it. The client still emits it — the plugin logs `CMD id=0x54 len=1` at the moment a game is left. A command the sender emits and the receiver's dispatcher ignores is a real asymmetry, recorded here rather than smoothed over. |

### 1.4 Who reads it

Four instructions, from an `XrefSweep.java` pass over the whole 480-byte range:

```
0x0048661C  MOV EDX,dword ptr [ECX*0x4 + 0x5005f8]   in FUN_004865D0  <- the dispatcher
0x004CDD04  MOV EDX,dword ptr [ECX*0x4 + 0x5005f8]   in FUN_004CDCE0
0x004CDE3A  MOV EDI,dword ptr [EAX*0x4 + 0x5005f8]   in FUN_004CDE10
0x004CE085  MOV EBX,dword ptr [EAX*0x4 + 0x5005f8]   in FUN_004CDFF0
```

Plus one raw-dword hit at `0x004BF9A9` inside code Ghidra never disassembled — reported as
UNCOVERED by the sweep's second pass rather than dropped, and not chased further here.

## 2. The dispatcher (`0x004865D0`)

`FUN_004865D0(int remainingBytes, int param2)` with the command stream in `EAX`. It walks the
stream, and for each command switches on `stream[0]`:

```c
switch (id) {
...
case 0x14:                       /* Right Click */
  remaining -= 10; consumed = 10;
  if (remaining < 0) goto abort;
  FUN_004C2370();                /* the handler */
  break;
case 0x1a:                       /* Stop */
  remaining -= 2;  consumed = 2;
  if (remaining < 0) goto abort;
  FUN_004C2190();
  break;
...
}
FUN_004CDE70(DAT_00512680);      /* per-command epilogue */
stream += consumed;
```

**58 opcodes have a case.** Every id outside that set is `default: goto abort` — the rest of the
turn's command block is discarded. That is why the plugin refuses to fan out an id it does not
recognise, and refuses to fan out a recognised id whose length disagrees with the dispatcher's:
either would hand this loop a byte count it did not expect and desynchronise everything behind it
in the same buffer.

### 2.1 The skip path

When `iVar2 != 0 && param_2 == 0` (a state in which most commands are not applied), the loop
does not switch on the handler at all — it looks the length up in the table at `0x005005F8` and
skips the command, with a special case restoring `2 + count*2` for ids `0x09`–`0x0B`:

```c
iVar4 = *(int *)(&DAT_005005f8 + id * 4);
if ((8 < id) && (id < 0xc)) iVar4 = (uint)stream[1] * 2 + 2;
remaining -= iVar4;
```

Eleven ids (`0x05`, `0x08`, `0x10`, `0x11`, `0x37`, `0x38`, `0x39`, `0x3A`, `0x3B`, `0x55`,
`0x56`) jump back into the switch even on this path — which is exactly why `0x37`'s table entry
is never used and may disagree.

## 3. The one property that decides the policy

Every handler was decompiled (`DecompileMany.java`, 55 functions) and classified by **how it
uses the receiving player's selection**. The iterator is
`getActivePlayerNextSelection` (`0x0049A850`), which walks `playersSelections[activePlayer]`
(`0x006284E8 + player*12`) from `selectionIterator` (`0x006284B6`) and returns 0 past slot 11 —
i.e. it walks the engine's own ≤12 selection and nothing else.

Three shapes, and only three:

| shape | code | meaning | count |
|---|---|---|---|
| **LOOP** | `selectionIterator = 0; u = next(); while (u) { …per unit…; u = next(); }` | the engine applies this command to **every** unit it holds | 20 |
| **SINGLE** | `u = next(); if (u) { v = next(); if (v == 0) { …} }` | the command does something **only when exactly one unit is selected** | 11 |
| **NONE** | never touches the iterator | selection-independent (chat, the select commands themselves, control groups, sync, alliance, …) | 27 |

`0x14` and `0x15` are shape **LOOP\***: the handler itself only unpacks the payload and forwards
to an applier — `0x004560D0` for Right Click, `0x0049AB00` for Targeted Order — and *that*
function runs the loop. Recorded explicitly in the table so it cannot be mistaken for NONE.

### 3.1 Why LOOP is the safe half of the rule

For a LOOP command the engine already does the thing to all twelve units it holds. Replaying it
against the units the cap hid is **the same operation over more units**, not a new one. This is
the whole basis of the feature: the plugin never invents semantics, it extends the engine's own.

### 3.2 Why SINGLE is the dangerous one

A SINGLE-gated command is inert at twelve units — it looks harmless to replay for exactly that
reason. But **a fan-out chunk can be one unit long**: 13 units selected means a chunk of 1 and a
chunk of 12. Replaying, say, Train against that would make it fire from the 13th unit, which the
player's own 13-unit selection never could. Every SINGLE opcode is passthrough.

### 3.3 The resource half of the rule

`0x00467250` is the spend:

```c
(&DAT_0057f0f0)[player] -= mineralCost[...];    /* two per-player resource arrays */
(&DAT_0057f120)[player] -= gasCost[...];
```

`0x00468280` is the cancel/refund path (through `0x0042CEC0` / `0x0042CE70`). A handler that
reaches either moves a **player-global** quantity, and a player-global effect is one the player
issued once, whatever the selection size. Four opcodes are LOOP-shaped *and* resource-moving —
`0x19`, `0x23`, `0x27` and (SINGLE anyway) `0x1F`, `0x35` — and are passthrough on that ground
alone. They are the most interesting rows in the table, because the shape rule alone would have
let two of them through.

## 4. The opcodes this task names

Named the way [`command-path.md`](command-path.md) §6 said it should be done — "pressing one key
in game names one id" — automated in `work/scratch/015/name-opcodes.ps1`: launch in `shadow`
mode (observe and log, change nothing), box a group, press one key, read the id the plugin logged,
re-box, next key. The whole alphabet was swept on the 24-unit Protoss group of
`Maps\campaign\(1)Enslavers02b.scm`, and again on `(1)Enslavers03a.scm`'s Terran group.

| key | command | evidence |
|---|---|---|
| S | **`0x1A` Stop**, 2 bytes | `CMD id=0x1A len=2 bytes=[1A 00]`, both maps |
| H | **`0x2B` Hold Position**, 2 bytes | `CMD id=0x2B len=2 bytes=[2B 00]`, both maps |
| A | `0x15` Targeted Order, order byte `0x08` (ground) / `0x0E` (on a unit) | `bytes=[15 6C 07 28 08 C0 0D E4 00 08 00]` |
| P | `0x15` Targeted Order, order byte `0x98` | `bytes=[15 6C 07 28 08 B7 0D E4 00 98 00]` |
| M | `0x15` Targeted Order, order byte `0x31` | `bytes=[15 6C 07 28 08 B7 0D E4 00 31 00]` |

Every other letter produced **nothing** on either group. That is itself a finding, and a
load-bearing one: see §8.

Two corroborations of the byte layout fall out for free — the order byte sits at offset 9 and the
queued flag at offset 10, exactly as [`command-path.md`](command-path.md) §5 read out of the
builder, and `0x1A`/`0x2B`'s second byte is the queued flag (0 with no shift held).

### 4.1 Handler corroboration

`0x1A`'s handler (`0x004C2190`) loops the selection and issues order `1` per unit through
`0x004754F0`; `0x2B`'s (`0x004C20C0`) loops and issues a **different order id per unit type**
(`0x39`, `0x3E`, `0x6C`, `0x88`, `0x6B` by type) — which is what Hold Position has to do, because
holding position is a different order for a ground unit and an air unit. The in-game run confirms
it from the other end: after Hold Position all 24 units of five different types end up on order
`0x6B` (§7).

```c
  selectionIterator = 0;

    u = getActivePlayerNextSelection();
    if (u == 0) {                               /* EXACTLY ONE unit selected */
      if (canBuild(activePlayer) == 1 && *(u16*)(cmd + 1) < 0x6a) {   /* a unit TYPE id */
        if (FUN_00467250(*(u16*)(cmd + 1)) != 0)   /* SPENDS MINERALS AND GAS */
          FUN_004743d0();
        ...
      }
    }
  }
}
```

A 3-byte command carrying a unit type id, gated on a single-unit selection, that deducts
minerals and gas. It is passthrough twice over.

## 6. Spell arbitration — there isn't any

The question this task was told to answer explicitly: *how does the engine arbitrate a targeted
cast across twelve selected casters?*

**It does not arbitrate.** `0x0049AB00`, the Targeted Order applier, is:

```c
FUN_0049a8c0(orderNeedsFormation[order]);      /* formation/centroid, not arbitration */
switch (order) {
  case 0x00: case 0x0f: case 0x14: case 0x19: case 0x1d ... case 0x9b:
    break;                                      /* these order ids do nothing here */
  default:
    selectionIterator = 0;
    u = getActivePlayerNextSelection();
    while (u != 0) {                            /* EVERY selected unit */
      if (canIssue(u) && ...) { ...give this unit the order... }
      u = getActivePlayerNextSelection();
    }
}
```

`FUN_0049A8C0` looked like the arbiter and is not: it accumulates the selection's bounding box,
centroid and total footprint area and writes them into the order context — group-move formation
state. It is called for Right Click too, with the same effect.

So the semantics at twelve are **all twelve act**, and there is no "pick one caster" path to
preserve. Fan-out at twenty-four therefore makes twenty-four units act, spending twenty-four
units' worth of energy.

**Is that a user-visible change?** For targeted casts, no: `0x15` has been in the fan-out set
since task 011 and this task changes nothing about it. What *is* new is the untargeted family —
`0x21`, whose handler deducts the unit's own energy (`0x00491B30` writes `CUnit+0xA2`) before
setting a secondary order. At twelve selected units the engine spends twelve units' energy; the
fan-out makes that twenty-four units' energy. That is the same rule applied to more units, and
it is stated here rather than buried because it is the one place where "the command applies to
all of them" costs something the player might not have intended.

Two further consequences of the same rule, flagged for the same reason:

- **`0x2A` / `0x5A`** collect units of one type into a 12-slot stack array and pair them up — a
  merge that consumes the units. Fanning it out merges within each chunk, so 24 units of the
  right type become 12 merged ones instead of 6. Semantically identical per chunk; twice the
  effect overall.
- **`0x36`** costs the acting unit HP (`0x004797B0`), not resources. Same story: more units, more
  HP spent, no player-global quantity touched.

## 7. What was proved, and how

### 7.1 In the live game, unattended

`tools/plugin/test-fanout-orders.ps1`. The oracle is the plugin's own `UNITSTATE` line: it walks
the **shadow list** — all 24 units, not the 12 the engine holds — reads each unit's current order
id from `CUnit+0x4D` and reports a histogram, on demand, triggered by the driver writing a marker
file. Run of 2026-08-08:

```
UNITSTATE [boxed]      n=24 live=24 visible=12 overflow=12 orders=[0x03:24] types=[0x41:12 0x54:2 0x16:1 0x42:4 0x46:3 0x15:1 0x44:1]
  Stop: the group is moving first (order 0x06 on 23 of 24 units)
  Stop: it was fanned out; 24 units were commanded; every chunk went out
UNITSTATE [stop-after] n=24 live=24 visible=12 overflow=12 orders=[0x03:24]
  -> NOT ONE of the 24 units is still on order 0x06

  Hold Position: the group is moving first (order 0x31 on 23 of 24 units)
  Hold Position: it was fanned out; 24 units were commanded; every chunk went out
UNITSTATE [hold-after] n=24 live=24 visible=12 overflow=12 orders=[0x6B:24]
  -> NOT ONE of the 24 units is still on order 0x31
```

The second half of each pair is the assertion that cannot be satisfied by a command that only
reached the engine's twelve: the other twelve would still be walking. `0 failure(s)`.

Attack and Patrol are confirmed in the same run to be `0x15` with distinct order bytes, and to
fan out — **already working via `0x15` since task 011**, no new code, checked here as a
regression. And the run asserts a whole-log invariant: every id that was fanned out
(`0x14 0x15 0x1A 0x2B`) is in the policy set, and ids seen but not fanned out
(`0x09 0x0A 0x0B 0x37 0x54`) were left alone.

`CUnit+0x4D` as the main order id is itself derived here: the `0x25` handler issues order `0x63`
and skips a unit whose `[+0x4D]` is already `0x63`, the `0x26` handler does the same with `0x62`,
the `0x2C` handler with `0x74`. `CUnit+0xA6` is the *secondary* order (the `0x22` handler sets it
to `0x6E`; `0x00491B30` sets it to `0x6D` after deducting energy) and is logged alongside.

### 7.2 Offline, byte-exact

`src/hooktest.cpp` part [9], no game and no hooks, against a fake module image:

- Stop (`0x1A`) against 36 units produces exactly 3 `Select`+order pairs, 84 bytes, with the
  right unit tags and the visible chunk last, and the order carried verbatim in each chunk.
- Hold Position with the queued (shift) flag set carries `queued=1` into every chunk — one
  queued order per unit, which is what the engine would have done to twelve of them.
- A 1-byte untargeted ability (`0x2A`) chunks correctly: 3 pairs, 81 bytes.
- **Ten passthrough ids are not duplicated**, at the same 36-unit selection: `0x1F`, `0x23`,
  `0x27`, `0x35` (resource-spending), `0x18`, `0x19` (cancel/refund), `0x20`, `0x0C`
  (single-gated), `0x13` (control group), `0x09` (Select). Each is asserted *not suppressed* and
  *nothing emitted*.
- The length guard: `0x1A` arriving at 3 bytes, `0x14` at 4 bytes, and an id the dispatcher does
  not accept are all refused rather than replayed.
- The whole set, both ways: all 19 fan-out ids fan out at their own dispatcher length, and all
  34 other accepted opcodes pass through untouched.

## 8. The fixture wall: no stock map can host a >12 untargeted-ability test

Acceptance criterion 3 asked for an untargeted **ability** fanning out in game. It needs three
things at once, and the stock map set cannot supply them together.

1. **More than twelve units in one drag box, owned by a human slot.** Rare: task 013 found only
   two maps in the 210-map set.
2. **All of one type.** In game a MIXED selection is offered only the basic command card. Swept
   directly: with the 24-unit five-type Protoss box of `(1)Enslavers02b.scm` selected, the entire
   alphabet produces exactly two commands, `0x1A` (Stop) and `0x2B` (Hold Position) — §4. No
   ability button exists to press.
3. **An ability needing no research.** Stim, Siege Mode, Burrow and Cloak all need it; a stock
   mission may or may not have pre-researched it.

Scanning all 210 stock `.scm`/`.scx` files for (1)+(2) — `work/scratch/015/scan_maps3.py`,
read-only via richchk — returns **one** map: `(1)Enslavers03a.scm` slot 6, 16 Marines, of which
at most **8** fit on one screen. It cannot be boxed. Every other human group over twelve units is
mixed-type.

That is a structural result, not bad luck, and a future task wanting the same fixture (a HUD row
for >12, say) will hit the same wall.

### 8.1 The generated-map route, and what it cost

The conductor amended the criterion to allow a map generated by `tools/make_test_map.py`
(task 009). Pursuing it found and fixed **two real bugs in that generator**, neither of which had
ever been caught because nothing had loaded its output in game:

1. **`OWNR` was written as `0x02` (`HUMAN_OCCUPIED`), not `0x06` (`Human (Open Slot)`).** `0x02`
   is what the game writes at runtime for a slot a human has *already* taken; what makes a slot
   available in the lobby is `0x06`. Every map the generator has ever produced was rejected with
   *"This map does not have a slot for a human participant."*
2. **The unit block grew right-and-down from the start location instead of being centred on it.**
   The camera opens centred on the start location and shows about 20×12 tiles, so the far half of
   the block sat off screen and behind the HUD where no drag box can reach it.

A third obstacle was found but **not** solved, and the ability test is not delivered in game
because of it: a map generated from a **melee ladder template** plays as a melee game even with
Game Type set to *Use Map Settings* — the player gets a standard starting base and the placed
units are never created. Proved from inside the process rather than from the screen: with the
generated 36-unit map loaded, the plugin's `UNITSTATE` reports
`types=[0x29:4 0x23:3 0x2A:1]` (four Drones, three Larva, one Overlord) and a ctrl+click reports
`types=[0x83:1]` (a Hatchery) — a Zerg melee start, containing none of the 36 units the map file
demonstrably holds. Generating from a stock **campaign** template instead produces a map that
loads and enters the mission (`player=1/1/1` in the log) but ends within about seven seconds,
consistent with a trigger misfiring after the CHK round-trip; two different campaign templates
behave the same way.

So the untargeted-ability fan-out is proved **offline and byte-exact** (§7.2, `0x2A` and the
whole 19-id set), and the untargeted **command** path is proved in the live game by Stop and Hold
Position (§7.1). Those two are the same code path as any other id in the set — the opcode is a
row in a table, not a branch — but the in-game ability run itself is not delivered. It is the one
gap in this task, and it is a fixture gap, not a feature gap.

## 9. Confidence and method

### Derived here, from this binary

- The command-length table's address, layout, extent and readers (§1).
